# 2026-11-05 主循环分段与重复发布优化

**分段计时与重复工作合并已完成，修正缓存一致性后主循环平均约 559 → 425 us（下降约 24.0%），但尚不满足 125 us。优化版仍发生 WKC 不完整，不能宣称稳定性通过。**

## 方法

- 延续 [ESC 读写优化](bench-timing-2026-11-05.md)，两组都使用 32 位主体＋字节尾部。
- 相同 125 us、RxPDO 131 B / TxPDO 410 B、0x76788646 布局签名，上位机实时优先级 80、CPU3，电机输出关闭。
- 两组使用相同的扩展分段计时，计数频率 24 MHz，计时代码默认关闭。RAM 统计只在测试结束后读取，实测包含中断、结束边界和计时自身开销。
- 优化前后各 3 轮有效样本；每轮最多 20 s，故障时提前退出。
- 掉电期间 SSH 连接超时的尝试没有产生有效样本；恢复后曾发现 RAM 快照不一致，因统计区未显式回写数据缓存。现已在退出 Active 后冻结统计并回写缓存，读取工具验证计数/最大值/总和/超时计数关系；本报告仅使用修正后重新采集的六轮数据，早期未回写快照全部排除。
- 平均值按样本数加权；最大值仅是本次观测值，不是最坏执行时间保证。分段存在嵌套，不能把所有行直接相加。

## 重复调用与改动

| 操作 | 原路径每轮调用 | 合并后每轮调用 |
|---|---:|---:|
| IO 服务 | 3.000 | 1.000 |
| 410 B ESC 写入 | 1.751 | 1.000 |
| CAN 排空 | 4.750 | 2.000 |
| 额外 CAN 编码 | 1.174 | 0.347 |

- Step 开始清除本轮 IO 服务标记，Application 派发后服务 IO 并标记完成；Poll 仅在没有应用服务时兜底，仍能发送停机保护帧。
- 移除前后 Poll 中额外调用 PDO_InputMapping 的路径。由 SSC 在本轮统一提交一次上行 PDO。
- 保留 Application 的 CAN 排空及映射前最后一次 CAN 刷新；额外 CAN 编码仍可更新本轮即将提交的镜像，但不额外写一次 ESC。
- SSC、Session、UART ACK、CAN 队列与 ESC 均仍由同一主线程拥有；未修改 ABI、白名单、20 ms 保护期限、WKC 停机规则或启用电机输出。
- 合并发布会改变 CAN 数据可见的时机：Poll 阶段新数据留至下一次 SSC 映射，不再立即单独写 ESC。本轮未测电机力矩输出和命令—应答端到端时延，不能把循环加速直接等同于所有链路延迟降低。

## 稳定性与当前部署状态

- 原路径：一轮约 6.4 s 因 WKC 不完整退出，另外两轮到 20 s 上限。
- 合并后：两轮到 20 s 上限，另一轮约 4.4 s 因 WKC 不完整退出。时长包含 SSH/启动耗时。
- 提前退出均为 operational=1、complete=0；从站仍 OP，主站 domain 不完整。
- 超时上限由 SIGINT 结束，返回 124；停止后的 master stopped/WKC 日志不作为提前失败。两组样本不足以比较故障率。
- 早期复测期间因电池耗尽出现 SSH 超时和 JTAG 全零；用户恢复供电后两者恢复。掉电失败样本不参与上述统计。
- 最后完成计时的是带缓存回写的合并版本；关闭计时的最终版本已构建，部署与烟测结果见下文。
- 用户随后确认电池耗尽并恢复供电。恢复后 SSH/JTAG 均重新可达；上位机源码差异、配置和构建检查通过，本地三个固件校验值与掉电前记录一致。Flash 与掉电前最后写入的 HEX 逐字节校验通过，共 196080 B；上位机源码仅保留预期的诊断信息改动，其余跟踪文件无差异，实时权限配置仍有效。验证范围为程序镜像及本次修改的上位机源码、配置。

## 后续异步与分批次方案评估

### DMA 和线程

- IMU 已使用 spi_transceive_cb + XDMA 异步采样；本次测到的是启动/完成处理等 CPU 路径，不能通过“再打开 DMA”直接消除。
- 可考虑把 IMU 传输推进、温控等放入独立工作线程，通过带序号/时间戳的固定快照交给 SSC；Session/ESC/保护所有权继续单一。
- 当前 Zephyr 仅启用 1 CPU。主线程优先级 0，Active 分支忙等 10 us 后再次运行；只增加低优先级工作线程可能无法及时获得 CPU，需要同时设计主线程的等待/唤醒和各任务期限。调度规则见 [Zephyr Scheduling](https://docs.zephyrproject.org/latest/kernel/services/scheduling/index.html)。
- 后续已完成独立 [ESC DMA 与 SM 交接验证](esc-dma-validation-2026-11-05.md)：双向搬运和尾字节交接通过，生产 SSC 异步接入及保护/abort 场景仍需单独验证。
- 真正异步还需要双缓冲及 in-flight/完成状态，DMA 完成前不能修改源镜像、提前交接 SSC 缓冲或复用目标。同步等待 DMA 完成不等同于流水化。
- 即使搬走 ESC 拷贝，RxPDO 验证、反馈采集/编码和 SSC 状态处理仍有成本；现有数据不支持承诺仅加 DMA 就达到 125 us。

### 参考 generic-usb-adapter 的分批次通信

已阅读 feature/generic-usb-adapter（75acdfbb77dfb061bfa9b80fe6f62035c397960c）：[USB 发送实现](https://github.com/HNUST-Dust/dust-adapter/blob/75acdfbb77dfb061bfa9b80fe6f62035c397960c/src/usb_reports.cpp) 中独立发送线程从队列取数据，CAN 每包最多六帧，不等凑满；优先回复，再交替处理 CAN 与传感器消息。

该调度思想可以借鉴到 EtherCAT，但当前 PDO 长度固定：分几次更新现有 410 B 镜像并不会让链路只传变化字段。若要降低周期影像容量，需要主从同步设计快区与带类型/序号的复用慢区，更新 schema/布局签名及协议版本。

建议快区保留会话、保护、命令和必要 CAN 反馈；慢区轮转 UART、IMU、诊断，明确每类数据最大等待时间、累计 ACK、重传、溢出和跨会话清理。轮转应按已确认的真实输入速率与期限设计，而非盲目降低 HI91/SBUS 更新率。DM 应按命令—应答判断，DJI 按 1 ms 周期检查。

USB 分支 CAN 上报每帧 24 B；当前 EtherCAT CAN 反馈每帧 19 B，不能假设直接复制 USB 包格式就能缩小 CAN 区。收益主要应来自按类型/频率调度和避免反复搬运慢数据。

本轮只完成单线程重复工作合并和方案评估，未引入新的 DMA 通路、多线程或新协议。
