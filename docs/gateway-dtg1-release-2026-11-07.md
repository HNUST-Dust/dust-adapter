真实 CAN 控制透传已补齐，正式镜像已部署。功能测试完成，所有非 SBUS 设备最大到达间隔 ≤ 2 ms 的性能目标尚未通过。固定下行 60 B、上行 180 B，EtherCAT 125 µs 交换，主站每 1 ms 更新六条命令，同序号命令保持至下次更新，从站去重。未运行实际平衡算法，也未测完整控制 RTT。

## 真实下行与保护

协议签名为 `0x44544731`（DTG1），替代旧实验签名。主站必须同步本仓库头文件及布局；旧签名不会启用真实透传。配套独立测试主站已同步，不代表已经完成实际 1 kHz 平衡控制器接入。

下行每条记录 10 B：设备类型 1 B、六条公共序号 1 B、原始 CAN 数据 8 B。整批解码和 YAML 白名单校验后才分发两侧，各通过独立 worker 进行三帧批量硬件提交。

| 设备 | 总线 | 命令 ID | 反馈 ID |
|---|---:|---:|---:|
| 右轮 | 0 | 0x200 | 0x201 |
| 右关节 B | 0 | 0x001 | 0x011 |
| 右关节 D | 0 | 0x002 | 0x012 |
| 左轮 | 3 | 0x200 | 0x201 |
| 左关节 B | 3 | 0x000 | 0x010 |
| 左关节 D | 3 | 0x003 | 0x013 |

仅配置白名单中的 ID/长度可发送，八字节负载按原样传递。驱动在接受硬件提交前独占完成回调，忙时不能覆盖在途回调。单次提交期限 1 ms；Stop、链路/传输错误、20 ms 新命令或输出看门狗触发保护，先中止待发命令，再发送配置保护帧。反复发送旧序号不能续新命令租约。

验收计数镜像的 [一分钟真实 CAN 测试](gateway-dtg1-clean-full-devices-60s-2026-11-07.json) 中，两侧各接收 60001 批、完成 60000 批（180000 帧），Stop 抢占并取消各最后一批，各完成一组保护帧，硬件错误 0。这是先前验收镜像的完成证明；最终固件不再含这些计数器，最终 JSON 的 60000 批是主站发起数，不能冒称为最终镜像的硬件完成计数。

[命令租约测试](gateway-dtg1-command-lease-2026-11-07.json) 在 1000 批后停止更新序号，仍重发旧安全命令及保活，约 1.019877 s 进入保护，两侧各完成 3000 帧及一组保护帧，无硬件错误。“slave protected”是该项故意触发看门狗的预期结果。

## 清理与调度修正

所有固件验收完成计数、运行时计时/IRQ/阶段探针及 ESC DMA 实验入口已撤除。到达间隔工具独立留在 tests/probes/device_pdo/host_bench.cpp，只在上位机手动启动，不编译进固件、不自动运行。正常故障状态保留单字节原因码，不做计时、累计或周期性跟踪。

清理后暴露了低优先级 PDO owner 的 SBUS 排队/确认停顿：故障块首次出队即已过期，临时快照记录到 21.4 ms；CAN 与传感器的独立交接仍可运行。PDO owner 与两个有界传感器 worker 改为同优先级 0，依靠现有休眠与 yield 轮转；CAN 两侧仍用最高协作优先级。SBUS 页保持到匹配 ACK，块确认依据会话与块序号，独立于心跳页新旧判断。20 ms 保护阈值保持不变。临时故障快照和首次出队计时代码随后全部撤掉。

此前提前保护的原始记录保留为 production-smoke、production-recheck、production-sbus-retry-failed、production-ack-independent-failed、production-priority1-failed JSON，不与本轮成功运行混用。最终 SBUS 最大间隔 15.50005 ms，符合其约 14 ms 的源周期量级；传感器最大间隔变大也说明公平调度存在代价，需要后续继续优化性能。

正常故障码：0 无故障/主动 Stop，1 命令校验，2 输出状态丢失，3 CAN 传输故障，4 输出看门狗，5 新命令看门狗，6 SBUS 数据过期，7 SBUS 编码失败。
