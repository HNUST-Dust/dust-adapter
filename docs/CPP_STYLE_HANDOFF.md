# C++ 编码风格与维护约定交接

更新日期：2026-10-24。适用于接手 dust-adapter、dust-control 的开发 agent。
本文记录用户明确认可的 C++ 编码与设计约定，可独立交给其他 agent 使用。
涉及具体工程的约定已单独注明；不要求为了形式整齐而扩大重构范围。

使用方式：将本文作为任务上下文，修改前阅读全文，并读取目标仓库适用的
AGENTS.md、构建说明和 `.clang-format`。修改后按文末清单自查。

## 核心标准

可读性：接手者能准确理解代码，快速找到行为入口，解释正常和故障路径。
可维护性：修改位置合理、影响范围可判断，修改后有针对性的验证依据。
代码短、文件多、抽象层多，都不自动意味着可读或好维护。

用户特别强调：代码既要在机器人上高效运行，也要像一篇文章一样让人类能够
阅读和 review。变量与函数必须定义在合理的位置，语句格式须符合人的审美。
命名语义清楚还不够，整体设计还要有对称性和稳定的组织规律。

## 定义位置与文件组织

- 局部变量靠近首次使用，作用域尽可能小；跨循环保存的普通状态放在循环前，
  不无故在循环体内使用 static。
- 多个不同含义的变量独立声明，不把能力、统计、会话状态挤在同一行。
- 常量、类型、实例与函数按职责和依赖顺序排列，让相关内容连续可读。
  不要在 UART 状态、回调与发送流程之间穿插 IMU 实现。
- 仅在必要时前置声明；能合理调整定义顺序消除声明时，优先调整顺序。
- 模块内部实现放匿名命名空间；对外接口放头文件，避免暴露无关实现。
- 少量线程的优先级常量放各线程所属实现文件，不维护共享的优先级头文件。
- 拆文件以职责、所有权和硬件边界为依据；避免为单个转调函数建立薄封装。
- LED/蜂鸣器指示逻辑与 IMU 加热 PWM、PID 分开；由运行时组合故障状态，
  不让两个模块互相依赖。

## 阅读顺序与收发对称性

先按职责组织，再在职责内部组织发送与接收。读者应能顺着模块找到类型、
状态和执行流程，不需要在 USB、CAN、UART 的零散定义之间来回拼接。

- 同一对象的请求与报告成对出现，例如 CanTransmitRequest 与 CanReceiveReport，
  UartTransmitRequest 与 UartReceiveReport。枚举、结构体和编解码接口采用一致顺序。
- 对称表示组织规律一致，不要求不同功能拥有相同字段、线程或空实现。
- 头文件先展示可理解的公共模型与接口，具体字节操作、私有辅助函数随后展开。
- 实现文件按职责连续组织；函数内部按校验、处理、提交结果的顺序阅读。
  出错路径可提前返回，避免把正常流程埋在多层条件中。
- 数值类型号也应按功能配对规划。已有协议变更必须同时评估两端、协议版本和
  测试，不能为了排列漂亮单方面改动线上含义。

## 排版与语句

使用仓库 `.clang-format`：Google 基础、C++17、80 列、4 空格缩进、禁用 Tab。
短函数除空函数外展开；if/else/for/while 使用大括号，不把条件与动作挤在一行。

```cpp
if (result) {
    QueueResult(request, result);
}
```

函数之间、完整逻辑单元之间适当留白。长调用、复杂条件按含义换行，避免
行尾注释把简单调用挤成奇怪的多行。注释较长时移到语句上方。

格式工具负责一致性，人工负责定义顺序、逻辑分段、注释位置和阅读节奏。
不要为了消除列宽问题机械缩写名称或增加无意义中间层。

## 命名与注释

- 名称应让人看出所属模块、操作对象及动作；有方向歧义时明确方向。
  例如 CanTransmitRequest、CanReceiveReport、UartTransmitRequest、UartReceiveReport，
  比通用的 Packet、Record、Data 更适合表达业务。
- 函数名表达动作与对象。EncodeCanTransmitRequest 表示编码，SendUart 表示发送，
  TakeUartChunk 表示取走队列数据；不要用 Handle、Process 掩盖具体职责。
- 名称结合命名空间和所属类阅读，避免机械重复前缀。不要为缩短名称丢失含义，
  也不要靠给所有变量加 USB/CAN 前缀代替模块划分。
- 协议中的发送/接收以 MCU 为参照：CAN 发送请求是上位机要求 MCU 向 CAN 发送，
  CAN 接收报告是 MCU 将 CAN 收到的数据报告给上位机。USB IN/OUT 按 USB 标准
  相对主机解释；注释和文档必须明确参照对象。
- 常量使用 k 前缀；类/结构体和函数延续现有 PascalCase，变量延续 snake_case。
  不为了风格统一单独改动外部 API 名称。
- 说明性注释使用中文，保留 SPDX、Doxygen 标签、代码名称与必要技术术语。
- 注释优先解释原因、约束和边界：回调上下文、所有权、硬件限制、生命周期、
  哪些操作不可撤回。避免重复函数名称或在多个位置复制同一段说明。
- 接口应说明是否阻塞、是否复制数据、缓冲区寿命及返回成功的真实含义。
  入队成功、硬件发送完成、设备确认是不同阶段，不能混淆。

## 协议与状态组织

- 公共协议头先用结构体展示消息字段，再提供显式 Encode/Decode 接口。
  读者应能直接看懂消息由什么组成，不必从偏移常量反推协议结构。
- 逻辑结构体表达含义，编解码器定义线上字节布局。不要将 packed struct 或
  reinterpret_cast 当作协议序列化；不要用 sizeof(逻辑结构体) 推导线上长度。
  固定长度与可变长度消息都遵守这个边界。
- wire 字节布局、端序、字段偏移和长度计算集中在协议层；业务代码使用具名字段，
  避免反复出现 request[9]、裸偏移和无解释的长度。
- 解码应校验长度、计数、枚举和有效范围，验证成功后才交给业务执行；明确解析
  失败时输出参数是否有效。容量、实际长度和记录数量不能混为一谈。
- 不必给所有数字机械命名；优先处理反复出现且有协议含义的字段和边界。
- 区分独占状态与跨线程状态，明确哪个线程能修改策略，哪些信息通过原子量、
  队列或锁传递。不要仅为减少全局变量而建立一个包揽所有状态的大对象。
- 错误码、统计计数和停止原因各司其职；明确错误是拒绝当前请求还是使会话失效。
- 维护协议两端的一致性；格式和注释变化也会影响副本比对。
  不擅自将本地修改描述为已同步到 dust-control。

## 平台边界：单 app、多 board

- 应用负责会话、白名单、FIFO、保护和发布策略；引脚映射由 board DTS/overlay
  表达，芯片寄存器及驱动实现留在支持仓库。
- 使用逻辑设备别名，避免业务层直接绑定物理 UART/CAN 编号。
- 硬件特有能力可以显式依赖，不要求所有调用都伪装成通用 Zephyr API。
  用户已决定：CAN 直接调用 hpm_support 的 hpm_can_send_batch()，删除应用
  can_backend 薄封装，不默认退化为单帧发送。
- 封装应承载完整操作与失败处理。例如 UART 接收启动组合回调安装、驱动启动、
  可选空闲检测和失败清理；只换个地方转调 prepare/start 收益不足。
- 不为当前没有的板卡虚构能力或宣称移植完成。通用代码路径构建通过，不等于
  其他板卡或硬件行为通过验收。

## 抽象与兼容内容

- 类和结构体用于表达真实概念、状态所有权和约束。不要为了减少参数数量，
  将无关字段装进一个 Context，也不要用继承或模板代替简单明确的关系。
- 抽函数应让调用处更容易理解，或集中重要约束与重复逻辑。只有重命名与转调、
  没有新增语义的包装通常应删除。
- 替换实现时检查调用方、生成脚本、测试、构建配置与文档。没有实际使用方的旧
  头文件、别名、构造函数和旧入口一并撤掉，不默认保留“以后可能用到”的兼容层。
- 确有外部使用者的兼容接口须有明确理由与边界，不能在不了解调用方时直接删除。
- 使用 RAII 表达资源生命周期；固件遵守禁用异常的构建约束，用明确返回值表达
  可恢复错误，不依赖 throw 或隐式异常路径处理输入校验。

## 修改和验证

- 修改前读取适用的 AGENTS.md，检查已有未提交改动，不覆盖其他 agent 的工作。
- 保持结构整理、行为改变、协议改变可区分；不在一次重构中同时修改控制算法、
  wire 定义和目录结构而失去归因依据。
- 使用格式检查、git diff --check、现有合约测试和相关固件构建验证。
  新增测试应守住重要行为，例如租约、会话隔离、保护和温控关断，避免镜像实现。
- 报告实际做过的验证和剩余边界；构建、测试通过不能当作硬件验收。
- 未获授权不刷板、使能电机或启动机器人。提交、推送、硬件操作状态必须如实说明。

本文不是“一律抽象化”或“一律拆小函数”的要求。内聚、顺序清楚的较长函数，
可以比散落在多个文件中的薄包装更容易维护。以理解成本和修改成本判断。

## 交付前自查清单

1. 不看实现，能否从名称判断模块、对象、方向和动作？
2. 同类收发定义是否相邻，类型、接口和实现的排列规律是否一致？
3. 变量是否靠近使用位置，常量与状态是否归属于真正负责它们的模块？
4. 头文件能否展示公共模型，私有细节是否留在实现边界内？
5. 正常流程与失败路径是否容易顺着读，成功的含义是否准确？
6. 是否引入了多余包装、无关状态容器、重复注释或无用途兼容入口？
7. 协议变更是否核对两端，生成内容和文档是否同步更新？
8. 是否遵循格式配置，完成与修改相关的检查，并如实报告验证范围？

遇到取舍时，优先保持语义准确、职责内聚、阅读顺序自然，再追求形式统一。
无需为了通过清单而引入当前需求不存在的抽象。
