# C++ 编码风格与维护约定交接

更新日期：2026-10-23。适用于接手 dust-adapter 的开发 agent。
本文总结用户在本轮明确认可的风格，不要求为了形式整齐而扩大重构范围。

## 核心标准

可读性：接手者能准确理解代码，快速找到行为入口，解释正常和故障路径。
可维护性：修改位置合理、影响范围可判断，修改后有针对性的验证依据。
代码短、文件多、抽象层多，都不自动意味着可读或好维护。

用户特别强调：变量与函数必须定义在合理的位置；语句格式须符合人的审美。

## 定义位置与文件组织

- 局部变量靠近首次使用，作用域尽可能小；跨循环保存的普通状态放在循环前，
  不无故在循环体内使用 static。
- 多个不同含义的变量独立声明，不把能力、统计、会话状态挤在同一行。
- 常量、类型、实例与函数按职责和依赖顺序排列，让相关内容连续可读。
  不要在 UART 状态、回调与发送流程之间穿插 IMU 实现。
- 仅在必要时前置声明；能合理调整定义顺序消除声明时，优先调整顺序。
- 模块内部实现放匿名命名空间；对外接口放头文件，避免暴露无关实现。
- 少量线程的优先级常量放各线程所属实现文件，不维护共享的优先级头文件。
- 拆文件以职责、所有权和硬件边界为依据；避免为单个转调函数建立薄封装。
- LED/蜂鸣器指示逻辑与 IMU 加热 PWM、PID 分开；由运行时组合故障状态，
  不让两个模块互相依赖。

## 排版与语句

使用仓库 `.clang-format`：Google 基础、C++17、80 列、4 空格缩进、禁用 Tab。
短函数除空函数外展开；if/else/for/while 使用大括号，不把条件与动作挤在一行。

```cpp
if (result) {
    QueueResult(request, result);
}
```

函数之间、完整逻辑单元之间适当留白。长调用、复杂条件按含义换行，避免
行尾注释把简单调用挤成奇怪的多行。注释较长时移到语句上方。

格式工具负责一致性，人工负责定义顺序、逻辑分段、注释位置和阅读节奏。
不要为了消除列宽问题机械缩写名称或增加无意义中间层。

## 命名与注释

- 函数名表达动作与对象，例如 CloseSession、HandleRequest、QueueResult、
  QueueStatus、ForwardRequest；重要操作避免只有 Close、Handle、Result。
- 常量使用 k 前缀；类/结构体和函数延续现有 PascalCase，变量延续 snake_case。
  不为了风格统一单独改动外部 API 名称。
- 说明性注释使用中文，保留 SPDX、Doxygen 标签、代码名称与必要技术术语。
- 注释优先解释原因、约束和边界：回调上下文、所有权、硬件限制、生命周期、
  哪些操作不可撤回。避免重复函数名称或在多个位置复制同一段说明。
- 接口应说明是否阻塞、是否复制数据、缓冲区寿命及返回成功的真实含义。
  入队成功、硬件发送完成、设备确认是不同阶段，不能混淆。

## 协议与状态组织

- wire 字节布局集中在协议层；业务代码优先使用具名字段访问，例如 RequestView，
  避免反复出现 request[9]、裸偏移和无解释的长度。
- 不必给所有数字机械命名；优先处理反复出现且有协议含义的字段和边界。
- 区分独占状态与跨线程状态，明确哪个线程能修改策略，哪些信息通过原子量、
  队列或锁传递。不要仅为减少全局变量而建立一个包揽所有状态的大对象。
- 错误码、统计计数和停止原因各司其职；明确错误是拒绝当前请求还是使会话失效。
- 维护协议两端的一致性；格式和注释变化也会影响副本比对。
  不擅自将本地修改描述为已同步到 dust-control。

## 平台边界：单 app、多 board

- 应用负责会话、白名单、FIFO、保护和发布策略；引脚映射由 board DTS/overlay
  表达，芯片寄存器及驱动实现留在支持仓库。
- 使用逻辑设备别名，避免业务层直接绑定物理 UART/CAN 编号。
- 硬件特有能力可以显式依赖，不要求所有调用都伪装成通用 Zephyr API。
  用户已决定：CAN 直接调用 hpm_support 的 hpm_can_send_batch()，删除应用
  can_backend 薄封装，不默认退化为单帧发送。
- 封装应承载完整操作与失败处理。例如 UART 接收启动组合回调安装、驱动启动、
  可选空闲检测和失败清理；只换个地方转调 prepare/start 收益不足。
- 不为当前没有的板卡虚构能力或宣称移植完成。通用代码路径构建通过，不等于
  其他板卡或硬件行为通过验收。

## 修改和验证

- 修改前读取适用的 AGENTS.md，检查已有未提交改动，不覆盖其他 agent 的工作。
- 保持结构整理、行为改变、协议改变可区分；不在一次重构中同时修改控制算法、
  wire 定义和目录结构而失去归因依据。
- 使用格式检查、git diff --check、现有合约测试和相关固件构建验证。
  新增测试应守住重要行为，例如租约、会话隔离、保护和温控关断，避免镜像实现。
- 报告实际做过的验证和剩余边界；构建、测试通过不能当作硬件验收。
- 未获授权不刷板、使能电机或启动机器人。提交、推送、硬件操作状态必须如实说明。

本文不是“一律抽象化”或“一律拆小函数”的要求。内聚、顺序清楚的较长函数，
可以比散落在多个文件中的薄包装更容易维护。以理解成本和修改成本判断。
